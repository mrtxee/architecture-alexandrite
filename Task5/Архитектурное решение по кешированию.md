## Предлагаемое решение

Исходя из того, что по предварительной оценке наиболее нагруженными сервисами являются Shop API, CRM API рекомендовано внедрить кэширование на уровне этих сервисов.

### Кэширование Shop API

Предлагается внедрить In-memory кэш в службу выдачи списка товаров.

Особенности службы выдачи списка
* Обновляется редко
* Операций чтения много
* Устаревание данных в кэше на период до 900 секунд является некритичным

Способ организации кэширования:
* Чтение данных: Cache-ahead / Pre-fetching
* Изменение данных со стороны пользователей не предусмотрено
* Вытеснение устаревших данных кэша обеспечивается методом time-based invalidation c TTL=860 секунд.
* Предусмотрена ручная инвалидация для менеджеров магазина


**Последовательность работы кэша товаров Shop API**

```mermaid
---
title: Кэширование товаров
config:
  look: handDrawn
---
sequenceDiagram
  actor User as User
  participant ShopAPI as Shop API Controller<br>(Spring Boot)
  participant Cache as Cacheable ProductService<br>(Caffeine / ConcurrentHashMap)
  participant Scheduler as ProductService<br>CacheRefresher
  participant DB as PostgreSQL
  autonumber
  Note over Scheduler, ShopAPI: При запуске сервиса
  Scheduler ->> DB: SELECT * FROM products WHERE active=true
  DB -->> Scheduler: Все товары
  Scheduler ->>+ Cache: put("all_active_products", data, TTL=860s)
  loop Каждые 860с
    Scheduler ->> DB: SELECT * FROM products WHERE active=true
    DB -->> Scheduler: Обновлённые данные
    Scheduler ->> Cache: refresh("all_active_products")
    Note over Cache: TTL сбрасывается
  end
  User ->>+ ShopAPI: GET /products?active=true
  ShopAPI ->> Cache: get("all_active_products")
  Cache -->> ShopAPI: Возвращает из памяти
  ShopAPI -->> User: 200 OK + JSON

```


### Кэширование CRM API

Предлагается внедрить In-memory кэш в службу выдачи списка заказов.

Особенности службы заказов
* Обновляется со средней частотой
* Операций чтения много
* Устаревание данных в кэше на период более 20 секунд является критическим

Кэширование в службах Списка заказов, Деталей заказа
* Чтение данных: Read-through
* Изменение данных: Write-through
* Trigger-based инвалидация и разогрев кэша

**Последовательность работы кэша заказов CRM API**

```mermaid
---
title: Кэшированик заказов
---
sequenceDiagram
  actor User as User
  participant CRM_API as CRM API<br>(Spring Boot)
  participant Cache as In-Memory Cache<br>(Caffeine / ConcurrentHashMap)
  participant DB as PostgreSQL

  User ->>+ CRM_API: GET /orders?user=123
  CRM_API ->> Cache: get("orders_123")
  alt В кэше есть
    Cache -->> CRM_API: [Order1, Order2]
    CRM_API -->> User: 200 OK + JSON
  else Нет в кэше
    Cache -->> CRM_API: null
    CRM_API ->> DB: SELECT * FROM orders WHERE user_id = 123
    DB -->> CRM_API: [Order1, Order2]
    CRM_API ->> Cache: put("orders_123", data)
    CRM_API -->> User: 200 OK + JSON
  end
  User ->>+ CRM_API: PUT /orders/456 {status: "shipped"}
  CRM_API ->> DB: UPDATE orders SET status='shipped' WHERE id=456
  DB -->> CRM_API: OK
  CRM_API ->> Cache: update("orders_123")<br>+ new order
  Note over Cache: Кэш актуален
  CRM_API -->>- User: 200 OK

```


## Мотивация

Кэширование является мощным инструментом горизонтального масштабирования производительности системы.

Правильно настроенный механизм кэша приводи к
* **Уменьшению latency**, времени отклика системы
* **Снижению нагрузки** на медленные системы (БД, файловую систему)

Правильная настройка кэширования включает в себя методы чтения кэша, обновления кэшированных данных, а так же политику вытеснения(eviction) кэша.

### Cравнение решений паттернов кэширования

| паттерн                    | описание                                                                                                                                                                                                                                                                                                                |
|----------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Read-through               | При запросе на чтение данных:<br>- Если cache-miss → дата-сервис обращается в БД<br>*Pros/Cons:*<br>✔ возвращаемые данные всегда актуальны<br>❌ производительность чтения зависит от качества настройки политики вытеснения кэша (cache eviction)                                                                       |
| Cache-ahead / Pre-fetching | При запросе на изменение данных:<br>- Клиент всегда получает ответ только из кэша.<br>- Если cache-miss → ошибка или null<br>- Обновление данных кэша происходит автономно асинхронно.<br>*Pros/Cons:*<br>❌ возвращаемые данные могут быть неактуальны<br>✔ производительность чтения высокая                           |
| Write-through              | Клиент дата-сервиса не знает о существовании кэша.<br>При запросе на изменение данных:<br>- Вначале меняется кэш, затем хранилище. <br>- Обновление данных происходит синхронно.<br>*Pros/Cons:*<br>✔ данные в кэше и в БД всегда актуальны<br>❌ производительность записи низкая                                       |
| Write-behind / Write-back  | Клиент дата-сервиса не знает о существовании кэша.<br>При запросе на изменение данных:<br>- Вначале меняется только кэш. <br>- Обновление данных БД происходит автономно асинхронно.<br>*Pros/Cons:*<br>❌ данные в БД могут быть неактуальны<br>✔ данные в кэше всегда актуальны<br>✔ производительность записи высокая |
| Write-around               | При запросе на изменение данных:<br>- Вначале меняется только состояние БД. <br>- Обновление данных в кэше происходит автономно асинхронно.<br>*Pros/Cons:*<br>✔ данные в БД всегда актуальны<br>❌ данные в кэше могут быть неактуальны<br>❌ производительность записи средняя                                          |

**Сравнение паттернов чтения кэша**

| паттерн                    | скорость чтения | гарантия согласованности |
| -------------------------- | --------------- | ------------------------ |
| Read-through               | 🐌              | ✔                        |
| Cache-ahead / Pre-fetching | 🐎🐎🐎          | ⭕                        |

**Сравнение паттернов обновления кэша**

| паттерн                   | скорость записи | гарантия актуальности кэша | гарантия актуальности данных |
| ------------------------- | --------------- | -------------------------- | ---------------------------- |
| Write-through             | 🐌              | ✔                          | ✔                            |
| Write-behind / Write-back | 🐎🐎🐎          | ✔                          | ⭕                            |
| Write-around              | 🐌🐌            | ⭕                          | ✔                            |
легенда:
* 🐎 – условная единица скорости обращения к памяти
* 🐌 – условная единица скорости обращения к системе хранения

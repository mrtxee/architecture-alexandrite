# Анализ проблем компании «Александрит»
> Планирование: анализ, идентификация проблем и поиск решений

## Существующие и потенциальные проблемные места
Проблемные места информационной системы компании в порядке снижения приоритета:
1. Перегружены базы Shop-DB, MES-DB
2. Отсутствует наблюдаемость системы, только мониторинг. Это исключает возможность проактивно реагировать на вероятный сбой.
3. Перегружен сервис MES-API, CRM-API
4. Не отлажена автоматизация и CI/CD-процессы
5. Отсутствует резервное копирование данных и протокол восстановления при сбое.
6. Требуется аудит информационной безопасности

## Инициативы по устранению проблем
### 1. Перегруженность баз Shop-DB, MES-DB
> жалобы от операторов: когда они заходят на первую страницу MES, система долго прогружается

Рекомендуется внедрить горизонтальное масштабирование сервисов MES-API, CPR-API путем построения CQRS-топологии на уровне системы хранения данных.

Для этого 
1. Выделить slave-репилики баз Shop-DB, MES-DB с полной физической репликацией.
2. Разделить запросы чтения/записи со стороны сервисов к соответствующим репликам базы
### 2. Отсутствует наблюдаемость системы
Для обеспечения возможности видеть тонкие места распределенной информационной системы, а так же проактивно реагировать на вероятные сбои, необходимо повысить степень наблюдаемости системы (Observability).

План
1. Поднять в среде контейнеры сервисов: 
	1. Prometheus
	2. Grafana
	3. Kibana
	4. ElasticSearch
	5. LogStash
2. Обеспечить сбор метрик сервисов MES-API, CRM-API
	1. Составить список критических метрик по RED и USE
	2. В приложениях настроить актуатор сбора метрик
		- eg. `http://<хост>:<порт>/actuator/prometheus`
	3. На узле Prometheus настроить сбор метрик по расписанию *(scraping)*
	4. В Grafana AlertManager настроить критические события
3. Обеспечить централизованное хранение логов
	1. В средах выполнения MES-API, CRM-API настроить Filebeat-агенты для передачи логов в Logstash
	2. В Logstash описать конвейер парсинга логов, преобразования их к единому стандарту при помощи Grok-правил и передачи в Elasticserch
	3. Elasticserch настроить политики обновления индексов. Наиболее быстрый доступ к логам должен быть в скоупе 30 дней.
	4. В Kibana настроить 
4. Обеспечить трасировку запросов по всем маршрутам между узлами MES-API, CRM-API, RabbitMq
	1. Каждый сервис подтягивает завиcимость на OpenTelemetry SDK
	2. OTel присваивает каждому запросу trace_id
	3. Каждый сервис при получении запроса формирует span с информацией о времени, продолжительность запроса и других параметрах запроса и передает его в ElasticSerach
	4. *todo: рассмотреть возможность передачи логов и метрик средствами OTel SDK*
5. В рамках бизнес-процессы предусмотреть наличие дежурно SRE, а так же политики реагирования при возникновении вероятных проблем.

### 3. Перегруженность сервисов MES-API, CRM-API
> заказ создаётся в CRM через получение сообщения из очереди от MES для кейса с внешними продавцами... жалоб от клиентов на просроченные заказы; 
> жалобы со стороны пользователей API. Представители компаний ежедневно сообщают, что не получили свои заказы.

Обеспечить автоматическую оркестрация над сервисами (запуск, масштабирование, перезагрузка).

План
1. Переносим все сервисы в Kubernates
2. Для внешних запросов поднимает узел с обратным прокси и распределением запросов
3. Используем Liveness Probes и алерты из Grafana, Kibana для управления перезагрузкой подсов
4. Horizontal Pod Autoscaler (HPA), а так же алерты для изменения числа запущенных узлов
	* в т.ч. масштабирование на основе числа не обработанных сообщений MQ
5. Helm / Kustomize для централизованного управления конфигурацией приложений

### 4. Не отлажена автоматизация и CI/CD-процессы
>- Деплой в dev-окружение осуществляется автоматически после мёрджа пул-реквеста и прохождения юнит-тестов.- В release-окружения версию деплоят вручную.- В продакшн версию тоже деплоят вручную.
>QA-инженер прогоняет E2E-сценарии вручную

План
1. В оба проекта добавляются инфраструктурные тесты
	* Юнит-тесты и инфраструктурные должны выполняться на стенде разработчика и в рамках PR 
2. QA инженер разрабатывает отдельный проект по проведению Smoke-тестов, которые тестируют результат выполнения основных безнес-сценариев с уровня UI.
3. Для активации возможности влить PR должны пройти успешно все 3 типа тестов.
4. Внедрить процесс ручного проведения серии ПСИ-испытаний с привлечением представителе от бизнеса (стейкхолдеров и пользователей).

### 5. Отсутствует резервное копирование данных и протокол восстановления при сбое

1. План резервного копирования данных
2. Chaos Engineering
	- Дважды в год, умышленно создаются ситуации утери данных, отказа инфраструктуры с целью проверки жизнеспособности протоколов восстановления и сборе готовность SRE совместно с разработчиками восстановить систему.

### 6. Требуется аудит информационной безопасности

> компания открыла свой API, который MES использует для расчёта стоимости изделия для обработки заказов другим продавцами

Передача данных наружу – риск потери данных. Хранение клиентских данных – риск нарушить законодательство. Хранение любых данных – риск нарушить гарантии Конфиденциальности, Целостности, Доступности данных.

Рекомендуется полный аудит безопасности информационной системы.

## Заключение

Все указанные проблемы распределенной информационной системы «Александрит» являются критически значимыми. Возможность решить их в пределах 6 месяцев зависит от объема ресурсов, которые компания готова выделить для обеспечения решения проблем.

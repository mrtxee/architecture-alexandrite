# Настройка мониторинга «Александрит»
> Выбор и настройка мониторинга в системе

## Мотивация

Обеспечения процесса постоянного сбора, анализа о состояния компонентов информационной системы позволит решить следующие задачи:
- Операционные цели
  - Обнаружение сбоев и проблем в реальном времени
  - Обеспечение доступности сервисов
  - Снижение времени простоя (MTTR)
  - Автоматическое оповещение ответственных лиц
- Аналитические цели
  - Анализ производительности системы
  - Планирование мощностей (capacity planning)
  - Выявление тенденций и закономерностей
  - Оптимизация ресурсов
- Бизнес-цели
  - Выполнение Service Level Agreement
  - Обеспечение качества обслуживания
  - Снижение операционных затрат

## Список метрик для отслеживания
Для полного мониторинга состояния распределенной информационной системы стоит использовать методологии USE и RED т.к. 
- **USE** помогает мониторить **ресурсы** (CPU, память, очереди, ошибки на уровне инфраструктуры).
- **RED** фокусируется на межсервисном взаимодействии (частота запросов, ошибки, время ответа).

* ### USE-метрики
	* Utilization (использование)
		* CPU % for shop API
			* Индикация степени утилизации ресурсов(mem, cpu) может выступать триггером для масштабирования системы.
		- CPU % for CRM API
		- CPU % for MES API
		- Memory Utilisation for shop API
		- Memory Utilisation for CRM API
		- Memory Utilisation for MES API
		- Memory Utilisation for shop db instance
		- Memory Utilisation for MES db instance
		- Size of S3 storage
			- скорость роста и критические показатели размера могут выступить в качестве индикаторов для
				- принятии решения в внедрении системы внешнего кэша
				- шардирования
				- пересмотра схем использования внутреннего кэша
				- принятия решений об оптимизации схемы хранения
		- Size of shop db instance
		- Size of MES db instance
	- Saturation (насыщенность)
		- Number of message in flight in RabbitMQ
			- сообщения «в полёте» (обрабатываются, но не подтверждены). Показывает нагрузку на брокер и возможные задержки
		- Number of connections for shop db instance
			- Перегрузка числа открытых сессий подключения может вести к исчерпанию лимита.
		- Number of connections for MES db instance
		- Number of simultanious sessions for shop API
			- Число активных сессий укажет на насыщенность сервиса пользователями
		- Number of simultanious sessions for CRM API
		- Number of simultanious sessions for MES API
	- Errors (ошибки)
		- Number of dead-letter-exchange letters in RabbitMQ
			- сообщения в DLQ (Dead Letter Queue). Сигнализирует об ошибках обработки (невалидные данные, сбои сервиса)
		- Number of HTTP 500 for CRM API
			- оценка числа сбоев в сервисе будет необходима для анализа и исправления ошибок в программе
		- Number of HTTP 500 for MES API
		- Number of HTTP 500 for shop API
- ### RED-метрики
	- Rate (частота)
		- Number of requests (RPS) for internet shop API
			- количество запросов в секунду. Базовый показатель нагрузки на сервис
		- Number of requests (RPS) for CRM API
		- Number of requests (RPS) for MES API
		- Number of requests (RPS) per user for internet shop API
		- Number of requests (RPS) per user for CRM API
		- Number of requests (RPS) per user for MES API
		- Kb tranferred (received) for shop API
			- объём принятых/отправленных данных (Кб/с) позволит оценить нагрузку по траффику и принять решение о балансировке числа узлов системы.
		- Kb tranferred (received) for CRM API
		- Kb tranferred (received) for MES API
		- Kb provided (sent) for shop API
		- Kb provided (sent) for CRM API
		- Kb provided (sent) for MES API
	- Errors (ошибки)
		- Number of HTTP 5xx, 4xx – анализ числа клиентских/серверных сбоев
		- Number of HTTP 3xx, 2xx – учет успешных ответов важен как база для расчёта качества работы системы ($success\ rate\ =\ 200 / total\ requests$)
	- Duration (длительность)
		- Response time (latency) for shop API
			- время ответа сервиса – ключевой показатель UX
		- Response time (latency) for CRM API
		- Response time (latency) for MES API

## Заключение

Метрик много не бывает. Анализ метрик является базой для уточнения требований к системе и выработки инициатив по оптимизации системы. Сокращения спектра наблюдаемости системы может быть проведено по согласованию инженеров нагрузочного тестирования, SRE, стейкхолдера проекта.
